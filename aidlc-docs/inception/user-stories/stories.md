# User Stories

형식: Given-When-Then 인수 조건, MoSCoW 우선순위(Must/Should/Could/Won't). INVEST 기준(독립적/협상가능/가치있음/추정가능/작음/테스트가능)을 만족하도록 작성.

---

## Epic 1: 회원가입 및 계정 관리 (Registration & Account Management)

### US-101: 이메일/비밀번호 회원가입
**페르소나**: 미인증 방문자
**우선순위**: Must
**스토리**: 미인증 방문자로서, 이메일과 비밀번호로 회원가입하여 구매자 계정을 만들고 싶다. 왜냐하면 그래야 플랫폼을 이용할 수 있기 때문이다.

**인수 조건**:
- Given 유효한 이메일 형식과 정책을 만족하는 비밀번호를 입력했을 때, When 회원가입을 요청하면, Then 계정이 생성되고 비밀번호는 BCrypt로 해시되어 저장된다.
- Given 이미 가입된 이메일로, When 회원가입을 요청하면, Then 중복 가입 오류를 반환한다.
- Given 비밀번호 정책(최소 길이 등)을 만족하지 않는 비밀번호로, When 회원가입을 요청하면, Then 유효성 검증 오류를 반환한다.
- Given 회원가입 직후, When 계정 상태를 확인하면, Then 이메일 미인증 상태(비활성)로 생성된다.

---

### US-102: 이메일 인증
**페르소나**: 미인증 방문자 → 구매자/판매자
**우선순위**: Must
**스토리**: 회원가입한 사용자로서, 이메일 인증 링크를 클릭하여 계정을 활성화하고 싶다. 왜냐하면 인증 전에는 로그인이 제한되기 때문이다.

**인수 조건**:
- Given 회원가입 직후 발송된 인증 이메일의 유효한 링크로, When 인증을 요청하면, Then 계정이 활성 상태로 전환된다.
- Given 만료되었거나 이미 사용된 인증 토큰으로, When 인증을 요청하면, Then 오류를 반환하고 재발송 옵션을 안내한다.
- Given 이메일 미인증 상태의 계정으로, When 로그인을 시도하면, Then 로그인이 거부되고 이메일 인증이 필요하다는 안내를 반환한다.

---

### US-103: 이메일/비밀번호 로그인
**페르소나**: 구매자, 판매자
**우선순위**: Must
**스토리**: 활성화된 계정을 가진 사용자로서, 이메일과 비밀번호로 로그인하여 Access/Refresh 토큰을 받고 싶다. 왜냐하면 그래야 인증이 필요한 기능을 이용할 수 있기 때문이다.

**인수 조건**:
- Given 올바른 이메일/비밀번호로, When 로그인을 요청하면, Then Access Token과 Refresh Token이 발급된다. (세부 발급 규칙은 US-301 참조)
- Given 잘못된 비밀번호로, When 로그인을 요청하면, Then 인증 실패를 반환하고 해당 시도가 Rate Limit 카운터에 반영된다. (US-402, US-404 참조)
- Given 존재하지 않는 이메일로, When 로그인을 요청하면, Then 계정 존재 여부를 유추할 수 없는 동일한 형태의 인증 실패 메시지를 반환한다.

---

### US-104: 비밀번호 재설정
**페르소나**: 구매자, 판매자
**우선순위**: Should
**스토리**: 비밀번호를 잊은 사용자로서, 이메일로 받은 재설정 링크를 통해 비밀번호를 재설정하고 싶다. 왜냐하면 그래야 계정 접근을 복구할 수 있기 때문이다.

**인수 조건**:
- Given 가입된 이메일로, When 비밀번호 재설정을 요청하면, Then 재설정 토큰이 포함된 이메일이 발송된다.
- Given 유효한 재설정 토큰과 정책을 만족하는 새 비밀번호로, When 재설정을 요청하면, Then 비밀번호가 변경되고 기존 Refresh Token은 모두 무효화된다.
- Given 만료되었거나 이미 사용된 재설정 토큰으로, When 재설정을 요청하면, Then 오류를 반환한다.

---

## Epic 2: 소셜 로그인 (Social Login)

### US-201: 카카오 로그인
**페르소나**: 미인증 방문자 → 구매자
**우선순위**: Must
**스토리**: 미인증 방문자로서, 카카오 계정으로 로그인하여 별도 비밀번호 없이 가입/로그인하고 싶다.

**인수 조건**:
- Given 카카오 OAuth2 인가 코드가 유효할 때, When 콜백을 처리하면, Then 카카오 계정과 연동된 로컬 계정이 없으면 신규 생성하고, 있으면 기존 계정으로 로그인하여 토큰을 발급한다.
- Given 이미 이메일/비밀번호로 가입된 이메일과 동일한 이메일의 카카오 계정으로, When 로그인하면, Then 계정 연동 정책에 따라 처리한다(연동 또는 별도 계정 생성 — 정책은 Application Design 단계에서 확정).
- Given 유효하지 않거나 만료된 인가 코드로, When 콜백을 처리하면, Then 인증 실패를 반환한다.

---

### US-202: 네이버 로그인
**페르소나**: 미인증 방문자 → 구매자
**우선순위**: Must
**스토리**: 미인증 방문자로서, 네이버 계정으로 로그인하고 싶다.

**인수 조건**: US-201과 동일한 구조를 네이버 OAuth2 플로우에 적용한다 (신규/기존 계정 처리, 인가 코드 검증 포함).

---

### US-203: 구글 로그인
**페르소나**: 미인증 방문자 → 구매자
**우선순위**: Must
**스토리**: 미인증 방문자로서, 구글 계정으로 로그인하고 싶다.

**인수 조건**: US-201과 동일한 구조를 구글 OAuth2 플로우에 적용한다 (신규/기존 계정 처리, 인가 코드 검증 포함).

---

## Epic 3: 토큰 관리 (Token Lifecycle)

### US-301: Access/Refresh 토큰 발급
**페르소나**: 구매자, 판매자, 관리자
**우선순위**: Must
**스토리**: 로그인에 성공한 사용자로서, 짧은 만료 시간의 Access Token과 긴 만료 시간의 Refresh Token을 받고 싶다. 왜냐하면 매 요청마다 재로그인하지 않으면서도 탈취 위험을 최소화해야 하기 때문이다.

**인수 조건**:
- Given 로그인 성공, When 토큰을 발급하면, Then Access Token에는 사용자 ID, 역할(Role), 만료 시간이 클레임으로 포함된다.
- Given 로그인 성공, When Refresh Token을 발급하면, Then MariaDB에 해당 토큰의 메타데이터(발급 시각, 만료 시각, 사용 여부)가 저장된다.

---

### US-302: 토큰 갱신 및 회전(Rotation)
**페르소나**: 구매자, 판매자, 관리자
**우선순위**: Must
**스토리**: Access Token이 만료된 클라이언트로서, Refresh Token으로 새 토큰 쌍을 발급받고 싶다. 왜냐하면 재로그인 없이 세션을 유지해야 하기 때문이다.

**인수 조건**:
- Given 유효하고 아직 사용되지 않은 Refresh Token으로, When 갱신을 요청하면, Then 새 Access/Refresh Token 쌍이 발급되고 기존 Refresh Token은 "사용됨"으로 표시되어 재사용이 불가능해진다.
- Given 만료된 Refresh Token으로, When 갱신을 요청하면, Then 재로그인이 필요하다는 오류를 반환한다.

---

### US-303: Refresh Token 재사용 탐지 및 토큰 패밀리 무효화
**페르소나**: 구매자, 판매자, 관리자 (보안 시나리오)
**우선순위**: Must
**스토리**: 시스템으로서, 이미 사용된(회전된) Refresh Token이 다시 사용되면 토큰 탈취로 간주하여 관련된 모든 토큰을 무효화하고 싶다. 왜냐하면 탈취된 토큰의 피해를 최소화해야 하기 때문이다.

**인수 조건**:
- Given 이미 "사용됨"으로 표시된 Refresh Token으로, When 갱신을 요청하면, Then 요청이 거부되고 해당 토큰 패밀리(최초 발급부터 이어진 모든 회전 토큰)가 즉시 전부 무효화된다.
- Given 토큰 패밀리가 무효화된 상태에서, When 해당 계정으로 유효했던 다른 Access Token을 사용하면, Then 다음 요청부터 거부된다(블랙리스트 반영, US-304 참조).

---

### US-304: 로그아웃 및 즉시 토큰 무효화
**페르소나**: 구매자, 판매자, 관리자
**우선순위**: Must
**스토리**: 로그인한 사용자로서, 로그아웃하면 즉시 세션이 종료되어 그 이후로는 기존 Access Token으로 아무 요청도 할 수 없기를 원한다.

**인수 조건**:
- Given 로그인 상태에서, When 로그아웃을 요청하면, Then 해당 Refresh Token이 즉시 폐기(무효화)된다.
- Given 로그아웃 직후, When 로그아웃 시점에 아직 만료되지 않은 Access Token으로 API를 호출하면, Then Redis 블랙리스트 조회 결과에 따라 요청이 거부된다.

---

## Epic 4: Rate Limit 및 IP 차단 (Abuse Prevention)

### US-401: 인증 엔드포인트 IP 기준 Rate Limit
**페르소나**: 시스템(전체 방문자 대상)
**우선순위**: Must
**스토리**: 시스템으로서, 동일 IP에서 인증 엔드포인트(로그인/회원가입 등)로 짧은 시간에 지나치게 많은 요청이 오면 제한하고 싶다.

**인수 조건**:
- Given 특정 IP가 정해진 시간 창(window) 내 허용치를 초과하는 요청을 인증 엔드포인트로 보낼 때, When 추가 요청이 오면, Then HTTP 429와 함께 재시도 가능 시간을 응답한다.
- Given 허용치 이내의 요청으로, When 인증 엔드포인트를 호출하면, Then 정상적으로 처리된다.
- Given Rate Limit 카운터는, When 여러 서비스 인스턴스에서 동시에 요청이 들어와도, Then Redis 기반으로 정확하게 합산된다.

---

### US-402: 계정 기준 Rate Limit
**페르소나**: 시스템 (특정 계정 보호)
**우선순위**: Must
**스토리**: 시스템으로서, 여러 IP를 바꿔가며 동일 계정에 로그인 시도가 반복되어도 해당 계정을 보호하고 싶다.

**인수 조건**:
- Given 동일 계정(이메일)에 대해 정해진 시간 창 내 로그인 실패가 임계치를 초과할 때, When 추가 로그인 시도가 오면, Then IP와 무관하게 해당 계정에 대한 로그인이 일시적으로 제한된다.
- Given 계정 제한이 걸린 상태에서, When 올바른 비밀번호로 로그인을 시도해도, Then 여전히 제한 해제 시간까지는 거부된다.

---

### US-403: Rate Limit 초과 IP 자동 차단
**페르소나**: 시스템
**우선순위**: Must
**스토리**: 시스템으로서, US-401의 Rate Limit을 반복적으로 초과하는 IP는 단순 429 응답을 넘어 일정 시간 동안 자동으로 차단하고 싶다.

**인수 조건**:
- Given IP가 Rate Limit을 초과한 상태가 지속/반복될 때, When 차단 조건을 만족하면, Then 해당 IP는 정해진 쿨다운 시간 동안 모든 인증 엔드포인트 요청이 차단된다.
- Given 차단된 IP로, When 쿨다운 시간이 지나기 전에 요청하면, Then 즉시 거부(403 또는 429)된다.

---

### US-404: 로그인 실패 반복 IP 자동 차단
**페르소나**: 시스템
**우선순위**: Must
**스토리**: 시스템으로서, 무차별 대입 공격이 의심되는(짧은 시간 내 다수 계정에 대한 로그인 실패가 반복되는) IP를 자동으로 차단하고 싶다.

**인수 조건**:
- Given 하나의 IP에서 정해진 시간 창 내 로그인 실패 횟수가 임계치를 초과할 때, When 다음 요청이 오면, Then 해당 IP가 자동 차단된다.
- Given 차단 사유(Rate Limit 초과 vs 로그인 실패 반복)는, When 로깅될 때, Then 감사 로그에 구분되어 기록된다(민감정보 제외, SECURITY-03/14 준수).

---

### US-405: 차단 자동 해제
**페르소나**: 시스템
**우선순위**: Should
**스토리**: 차단된 IP의 사용자로서, 정해진 쿨다운 시간이 지나면 별도 조치 없이 다시 정상적으로 서비스를 이용하고 싶다.

**인수 조건**:
- Given 차단된 IP가, When 쿨다운 시간(TTL)이 경과하면, Then Redis에서 차단 키가 자동 만료되어 별도 해제 작업 없이 다시 요청이 허용된다.

---

## Epic 5: RBAC / 인가 (Authorization)

### US-501: 역할 기반 접근 제어
**페르소나**: 구매자, 판매자, 관리자
**우선순위**: Must
**스토리**: 인증된 사용자로서, 내 역할(USER/SELLER/ADMIN)에 맞는 기능에만 접근하고 싶다(또는 시스템 입장에서는 그렇게 강제하고 싶다).

**인수 조건**:
- Given 유효한 Access Token의 역할 클레임이 요청한 엔드포인트에 필요한 역할과 일치할 때, When API를 호출하면, Then 요청이 허용된다.
- Given 역할이 일치하지 않을 때, When API를 호출하면, Then HTTP 403이 반환된다.
- Given 토큰이 없거나 유효하지 않을 때, When 인증이 필요한 API를 호출하면, Then HTTP 401이 반환된다(Deny by default).

---

### US-502: 관리자 전용 기능 접근 제한
**페르소나**: 관리자
**우선순위**: Must
**스토리**: 관리자로서, 관리자 전용 기능(예: 사용자 관리)에 오직 ADMIN 역할만 접근할 수 있도록 서버 사이드에서 강제하고 싶다.

**인수 조건**:
- Given ADMIN이 아닌 유효한 토큰(예: USER, SELLER)으로, When 관리자 전용 엔드포인트를 호출하면, Then HTTP 403이 반환되고 클라이언트 측 은닉에 의존하지 않는다(SECURITY-08).

---

### US-603: 미인증 요청의 일관된 차단
**페르소나**: 미인증 방문자
**우선순위**: Must
**스토리**: 미인증 방문자로서, 이 서비스의 공개 엔드포인트(회원가입/로그인/소셜 로그인/토큰 갱신 등) 외의 모든 요청은 일관되게 거부되기를 원한다(그래야 어떤 API가 보호되는지 예측 가능하다).

**인수 조건**:
- Given 토큰 없이, When 공개 엔드포인트가 아닌 이 서비스의 경로를 호출하면, Then 항상 동일한 형식의 HTTP 401 응답을 받는다.
- Given 토큰 없이, When 공개 엔드포인트(회원가입/로그인/소셜 로그인 시작/토큰 갱신)를 호출하면, Then 정상 처리된다.
